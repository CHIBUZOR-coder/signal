D — Architecture & data control (slides 15–17)

One codebase, isolated per client

Web, mobile, and SAP/file imports are all "thin clients" — no rules, no authority decisions live in any of them. Each client gets its own environment; nothing is shared between clients but the container image.

  • API: a modular monolith (NestJS/TypeScript) with an authority policy engine checking role × scope × authority × materiality × delegation on every request.
  • A separate calculation engine — pure, versioned, exact-decimal math.
  • One PostgreSQL database per client: current state, append-only ledgers, Gate/Review snapshots, config versions, a hash-chained audit log.
  • Background workers for imports, reports, ageing, escalation, delegation expiry.
  • Evidence in its own S3 bucket with its own KMS key, malware-scanned.

What changes vs. what never can (slide 16)

Versioned, changes

  • Opportunity / Draft
  • Initiative details, Control State
  • Latest Forecast
  • Decisions, Commitments, Blockers

🔒 Immutable once written

  • Gate decisions & snapshots

  • Value claims, Finance decisions
  • Delivery & Banking Ledgers
  • Review Snapshots, Calculation Context

Corrections never overwrite — they're new, linked records (Value Adjustment, Banking Adjustment, Review Addendum, Resubmission). Enforced at the database level: the app's own role has no UPDATE/DELETE on immutable tables, triggers reject any attempt, and the audit log is hash-chained.

Reproducing March's number in September (slide 17)

Closing a review writes an immutable snapshot of the values and the full calculation context used to produce them — gate factors, FX rates, structure, engine version, as-of time. Every later migration has to re-run that exact calculation and match it to the cent, or the migration fails (AT-17).

E — Value-control scenarios (slides 18–20)

Four worked examples the deck uses to prove the controls hold under real numbers.

1. Partial validation

A $700k claim, Finance validates $620k. Delivered rises by exactly $620k — the $80k gap doesn't vanish, it ages in a queue until new evidence justifies a new tranche. Tranches can never exceed the original claim (a database constraint).

2. MAPV — Maturity-Adjusted Portfolio Value

Formula: Validated Delivered + (Gate factor × eligible remaining value). Worked example: $3.0m + 83.3% × $7.0m = $8.83m. Challenged or unsupported remaining value counts as zero until re-assured — never discounted twice.

3. A challenged PG4 initiative

The Gate stays at PG4 — history is never rewritten — but a separate Control State flips to "Re-assurance Required." The Original Commitment stays frozen; only the Forecast moves, opening a Value-at-Risk gap. In the worked example, MAPV drops from $7.58m to $5.92m to reflect the challenge.

4. Banking and delegated authority

Delivered → Finance-validated → (CFO certified, above a materiality threshold) → Banked. The person who validates a value can never also bank it (segregation of duties). A CFO can delegate banking up to a ceiling — e.g. $2m — to a Finance Director; anything above that ceiling always stays with the CFO, it never falls through to the delegate.

F — Security & resilience (slides 21–22)

Client isolation

A compromise of one client's environment — app, database, evidence bucket, encryption keys, logs, backups — has no network route to any other client's. Fully separate per client.

Identity & access

  • MFA required for privileged roles; SSO-ready (OIDC/SAML); step-up re-authentication for material actions
  • A sealed, alerted break-glass account for emergencies
  • No standing production access — just-in-time, approved, time-boxed, logged, Praxis notified, auto-revoked

Release pipeline & backups

  • Every change: second reviewer, automated SAST/dependency/secret scans, staging with dynamic scanning, manual approval before production
  • Point-in-time recovery (RPO in minutes), restore target of 8 hours (RTO)
  • Daily encrypted snapshots copied to a second region; restore proven before go-live, then quarterly
G — Delivery, scale & costs (slides 24–28)

Timeline

18 weeks including a contingency week, with the first end-to-end flow demoed by week 9.

One product, many clients

One codebase, one release train — every client upgrades the same way. A client request becomes configuration, a product enhancement for everyone, or an integration adapter — never a custom one-off fork. SAP stays read-only: data imports through a validate → preview → reconcile → confirm pipeline, never written back, and imported data still has to pass the normal validation workflow before it counts as Finance-validated or Banked.

Costs

Roughly ₦280k per production client plus a shared staging environment — costs scale close to linearly with the number of clients, not with added complexity.

Testing discipline

Calculation, permission, and immutability tests run on every single build. The team would delay launch for any of: cross-client data exposure, the possibility of double-banking, an alterable "immutable" record, a bypassable authority check, or an unproven restore.

H — Ownership & handover (slides 29–30)

Praxis owns everything from day one — source code, cloud accounts, databases, encryption keys, CI/CD, mobile store accounts, SSO config, monitoring, backups. Nothing is held hostage by the vendor.

If Auracule left tomorrow: Praxis revokes access and rotates secrets, a new team reads the runbooks and architecture decision records, runs a rehearsed deploy-and-restore, and releases through the same pipeline.

What's needed from Praxis, and when

Things like the signed SOW and GitHub/AWS accounts before week 1, the Authority Matrix by week 2, SSO provider details by week 8, pilot UAT users by weeks 15–16 — most marked critical-path, meaning a delay here delays the whole project day-for-day.
